# PortingWork

## PR Porting

移植其他 Cataclysm 分支或上游的改动时，请按照本规范进行：

### 确认来源与可移植性

- 确认源仓库、提交或 PR、目标行为、作者和适用许可证。以原始补丁、提交记录和项目说明为依据，不凭记忆复述来源。
- 阅读完整 PR 描述和差异，确认改动范围、依赖和关联功能。识别混在同一补丁中的无关行为，不能因为补丁可应用就认定全部适合移植。
- 对照 CCB 的当前实现、数据结构、调用方、注册、声明和测试。不同fork同名接口可能有不同语义，反之不同名接口也可能出现语义相同，需逐项核对。
- 确认是否已有相同行为，或是否可通过较小的兼容实现达到目标。若源代码与 CCB 差异很大，移植可能不再是原始改动的直接延续，应作为实现参考另行评估。
- 多个大型 PR、多名作者、复合了独立功能、来源或许可不清、或有多种合理适配路径时，先向维护者确认范围、署名和拆分方式。

### 应用补丁与适配

1. 优先取得可追溯的原始 patch 或提交内容，保存来源链接和版本信息。检查补丁内容后再应用，不直接执行来源不明的脚本或构建步骤。
2. 补丁可以应用时，核对应用后的差异和冲突解决；不能应用时，按文件及功能单元对照原始改动和 CCB 代码，保留可验证的源行为，避免整片照抄后再整体重写。
3. 先理解原始实现的意图、边界和依赖，再适配 CCB 的类型、接口、数据格式、错误处理、生命周期和测试惯例。适配不得默默改变原功能目标。
4. 需要区分源改动和本地适配，对于代码相近的分支可以一次性完成，但若原始代码来自差距极其巨大的分支，项目流程要求分开记录原作者贡献与后续兼容改动，不得为了方便把本地新设计归到原作者名下。
5. 正确保留作者及共同作者信息，并遵守源项目和本仓库许可要求。作者归属应通过仓库认可的贡献元数据表达；不在代码注释、PR 描述或提交说明中捏造作者或用文字标记替代正式署名。

### 验证

- 将源补丁与最终改动逐项比较，确认目标行为没有遗漏，冲突处理没有引入静默语义变化。
- 检查 CCB 特有的前置条件、旧数据、接口兼容、错误路径和运行时边界。
- 运行与改动直接相关的格式、数据契约和聚焦测试；按影响范围补充测试。未运行的宽范围验证要如实说明。
- 交付时列明来源仓库与提交/PR、移植范围、本地适配、署名处理、验证结果和仍存在的差异。

## Other Porting

除移植来自其他分支的功能外，项目开发过程中还可以存在一些项目内或仓库与本地项目间的移植工作，其需要注意：
 - 移植流程可参考 PR Porting ，但不应生搬硬套。
 - 项目内部移植/迁移流程无需额外署名；移植外部本地项目时，是否需要额外署名应听从人类指令，若无指令不擅自猜测询问。

### core migrating to mod

如果要将核心数据(`data/json`/modid=ccb)迁移到内置第一方模组，应额外注意:
 - 必须为核心添加对应的obsoletion/migration配置，确保旧存档不会因为物品被迁移/删除而报错。
 - 需要为迁移至mod后的数据id添加mod独有的前缀/后缀或其他识别符，保证条目id不与被核心migration的一致，避免mod项目因核心migration数据消失。
   + 例如，Aftershock: Exoplanet使用`afs_*`、Futurism Cataclysm: Legacy使用`fcl_*`等。
 - 需要为迁移至的mod同样配置migration数据，将其迁移至mod内对应物品，防止在加载了对应mod的情况下仍然被核心迁移为其他项目。

### mod porting to mod

如果要将一个mod中的物品移植到另一个mod中，应额外注意：
 - 需要完整迁移该物品相关上下文，避免跨mod引用。
 - 如果mod条目数据id具有独有的前缀/后缀或其他识别符，应该替换为被迁移后的mod的，而非将其保留。
 - 如果mod互相冲突，请勿处理不在预期内的`mod_interactions`等仅二者同时出现时才需考虑的内容。
 - 如果mod互相兼容，且都为第一方mod，需要考虑当两个mod同时在存档中加载如何处理。

### mod migrating to core

如果要将mod内容移植到核心，应额外注意：
 - 如果id相同，则这种移植不应该添加obsoletion/migration配置，因为核心模块(`data/json`/modid=ccb)在预期内是必须加载的基本项目。
 - 如果id不同，例如需要去除数据id中mod独有的前缀/后缀或其他识别符，应将migration配置留在mod中而非错误写入核心数据。
