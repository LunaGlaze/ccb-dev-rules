# PRDraft

用户可能会要求起草、整理或发起PR，此工作严格遵循本文档要求。

## 基本要求

 - 依照`.github\pull_request_template.md`模板，根据用户要求将草稿写入临时目录、输出至会话，或提交至远端；如果项目内没有临时目录，不应放置到全局临时目录(如`%TEMP%`)，而应在工作区内创建以`.`开头的不被git版本管理追踪的目录用以存放临时文档；未使用或无需使用的章节无需强行填入内容。
 - 草稿需要依照去AI味Skill(若有)和`DocDeAI.md`去除AI痕迹，例如避免`不是..而是`、`拆开揉碎`等表达，只应保留合理的陈述分类/点格式
 - 无论使用何种语言作为主要语言，对于json配置/代码内有明确原文的应优先使用对应原文
 - 明确 PR 的性质是面向最终结果而非实现过程
   + PR 描述的状态是最后一次提交时的整个工作区，而非具体工作流程
   + 禁止将会话或草案的内容写入改动内容中，只允许描述最终状态
   + 不说“不做什么”，只说“做了什么”，禁止解释或说明为何不做/人类让你删掉/无需做什么
   + 不应在草稿中提及自己做错了什么或讨论了什么而导致了什么修改
 - 明确 PR 同时面向审核者和玩家用户，叙述偏向应当保持适当，不应全部过细解释也不应全部引用代码修改例
 - 不在应该描述背景的场合描述 PR 做了什么，也不在描述做了什么的章节描述没做什么；明确章节的职权边界

## 依据与结构

- 以最终工作区的实际改动、验证结果和已确认需求为依据。不要把早期草案、临时计划、讨论过程或后来已撤销的方案写成最终内容。
- 先判断模板各章节分别要求什么信息，再填入对应内容。背景章节解释问题和必要上下文；改动章节说明最终行为；测试章节只写实际运行的验证；影响章节说明玩家或维护者可观察到的变化。
- 没有适用内容的章节按模板规则处理，不为了填满模板编造背景、测试或影响。不要把同一段文字复制到多个章节。
- PR 标题和正文应具体、简洁。按项目约定使用适当语言；代码标识符、JSON 原文和专有术语保持准确。

## 内容边界

描述最终状态，不写逐步实现过程、会话内容、工具操作、自动化修改记录或个人自评。说明做出的改动及其真实影响；不要用解释“没有做什么”来替代结果，也不要留下已经废弃的决策和阶段计划。

背景、实现和验证各自承担不同信息。不要在背景里重复实现清单，不要在实现章节写无关动机，不要把未运行的检查描述成通过。对尚未确认的兼容性或效果，明确限定范围或暂不作结论。

PR 描述的责任人应由项目参与者明确承担。自动化协作工具不能替人类承担审查、合并或发布责任；具体 Responsible human 按项目的 PR 模板和维护安排填写，不猜测账号或身份。

## 完稿检查

核对标题和章节是否符合当前模板；每项陈述是否能由最终 diff、需求或实际验证支持；背景、改动、测试和影响是否放在正确位置；是否残留草稿标记、重复句、过程叙述、未经证实的保证或不自然的模板套话。

# 流程建议

无论如何，本Skill不建议智能体全权处理完整工作流程，PR提交应该首先让人类审阅有关代码和PR内容草案后再做最终提交；人类应有能力理解并审核diff内容，有能力承担PR责任。最理想的情况应由人类亲自缮写或手动修改AI成稿后才进行提交。
