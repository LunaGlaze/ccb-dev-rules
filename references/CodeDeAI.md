# CodeDeAI

所有涉及 C++ 或 Lua 的编辑工作都应该遵守本文件原则，核心原则包括：
 - 代码实现、修复和重构时应贴合 CCB 现有代码
 - coding需要保证行为正确、修改克制、可读性自然
 - 避免极端的过激工程化或过激防御性编程

本文件只约束AI行为，不得用此集越权向人类提出要求。

## 基本流程

### Pre: read code

动手前需要首先阅读相关代码，应首先确认行为的定义、入口、调用、依赖的位置和数据。按改动选择目标文件、相邻实现、注册处、声明、Schema、测试和目录规则。需要调查dda/tlg/bn等其他分支代码时，应先核对本仓库版本及差异；同名类型、函数或数据字段不保证语义相同，不同名函数或参数也可能仅为不同项目命名区别。

修改既有行为时，明确当前行为、目标行为和受影响边界。若需求描述与源码观察不一致，应先查证并向用户说明差异，不应把推测当作规则。除非有明确重构需求，不把局部修复扩大成目录整理或架构迁移。

### 代码取舍

- 选择本仓库现有且最直接的模式。新增 helper、类型、状态层、包装函数或配置项之前，先确认相邻代码没有可复用的实现。
- 函数按行为和生命周期组织。不要为每个表达式拆函数，也不要把一个有清晰职责的流程切成许多只转发参数的空壳嵌套。
- 名称应说明领域对象和行为。优先用项目已有术语；不要默认全部使用 `temp`、`helper`、`manager` 等缺少语境的名字、避免把局部变量写成一整句说明。
- 注释应该少而有效。注释应说明理由、限制、算法来源或不明显的行为，不要写“这里检查是否为空”这类代码已经直接表达的内容。
- 不为显得稳健而重复校验。类型、所有权、调用契约和上游逻辑已经保证的条件无需在每层重验。外部输入、文件、网络、脚本边界及可能失效的资源仍需进行合适检查。
- 不吞掉错误，也不要把每种失败都转换成相同的通用结果。按既有接口传播、处理或呈现错误，保留调用方判断所需的信息。
- 避免复制已经存在的算法、数据和接口。若逻辑确实需要共享，按项目现有的模块边界整理，不因局部重复两行就创建公共框架。
- 保留既有行为和数据兼容性。纯结构性清理应与功能修复分开判断，不能借去除重复代码之名改变可观察行为。

### C++ 关注点

遵循目标目录的格式文件和相邻实现，检查对象所有权、引用和指针有效期、析构与异常路径、容器迭代器失效，以及状态修改是否可能在多处生效。使用仓库已有的资源管理和生命周期模式，不引入陌生的智能指针或包装抽象来替代对现有所有权关系的理解。

涉及公共函数、事件、注册、序列化、JSON 加载、Lua 绑定或共享状态时，追踪完整调用路径，并检查兼容调用方。对生命周期、边界条件和状态转换的行为变化，应以聚焦测试或可复核的验证覆盖。不要只凭成功编译判断逻辑正确。

同步 C:DDA 等来源的变更时，保留与上游后续同步相关的结构和语义。大规模改写若能显著降低复杂度或满足明确需求可以进行，但应先界定范围、验证策略和同步影响，不把“减少冲突”误解为任何重构都不允许。

### Lua 关注点

Lua 行为以仓库支持的入口、注册、声明和运行时为准。检查调用方实际传递的数据、可选字段、返回值、错误传播和原生侧生命周期；不能因 Lua 语法熟悉就假定接口和其他项目相同。

修改 Lua 公共接口时，同步检查注册位置、LuaLS 声明、相关契约和生成清单的维护方式。生成文件按既定工具更新，不手工改写。按本次改动选择聚焦的 Lua 检查，不要求无关的全量审计。

### Post: Review before completion

回看完整 diff，确认每处改动都服务于目标，新增保护确有风险依据，删去的代码没有承担隐含契约；检查错误路径、边界和调用方；运行与改动对应的格式、静态或聚焦测试。若未能验证某项行为，在交付说明中指出具体缺口。

## 禁忌事项

以下列出各种智能体辅助编程时常见的不良习惯或可能影响仓库整体代码干净程度的行为，实际编程过程中应该极力避免：
 - 高密度通用标识符: `temp, tmp, utils, helper, manager, handler, obj, arr, elem` 等大量堆积，且与附近代码上下文类似功能范例不一致。
 - 高注释比例: 大量带有解释性(explanatory, not why)的注释内容、不遵守skill入口注释逻辑要求的非必要注释、注释内带大量括号等。
 - 强迫性空值防御: 冗长的明确空值守卫(`== null`、`!= null`、`!!`)大量涌入，即`if (x == null) return`/`obj!!`风格。少数的非空检查是正常的，但每段函数密度≥2个的此类保护很可能实际表明模型强迫性地将每个值不必要地包裹在空检查中。
 - 过度解释性命名: just like 5+ snake_case segments (`total_score_for_all_users_in_the_list`)，强迫性地在每个变量或函数名称中解释一切；除部分API等所需camelCase长名称外，此类命名应主要采用简短泛名，通常不超过2~3个`_`使用。
 - 未被要求的“灵活性”或“可配置性”: 对只用一次的代码抽象一套框架，或对只在极少个例调用且人类没有给出复用/接口需求的功能，强迫性添加配置选项或数值接口。
 - 自我感动式error防御: 为不可能发生的场景写错误处理，或在被调用函数(通常是输出)中为应该由调用函数处理或避免的非规范调用方式进行防御。
 - 绕路实现: 对可简单实现的功能，强迫性进行多层无意义嵌套，或因拒绝理解相关数据或函数真实含义导致以完全错误或与正常相反的逻辑曲折实现。
 - 过度思考: 对不涉及极复杂系统的任务思考超过10分钟不肯动手执行、对多个没有明确前后关联或后者无需基于更前者实现的小任务强迫性调查玩全部的每一个细节后才肯执行。浪费时间与token在无意义的thinking中。
 - 范围膨胀(Scope creep): 修一个问题，顺手重构无关模块。必要的调用方、数据迁移和测试要一起处理；没有当前用途的扩展就停下。
 - 无用防御(Hashing & hypothetical hardening): 没人读取的 checksum、为想象中的未来搭的兼容层；或为任何改动都进行大量测试。防御要能发现问题，并触发拒绝、恢复或诊断。有效的保留，无用的省掉，吞错报成功或制造重复副作用的修好。
 - 意图越界(Intent violation): 在要求只有review/调查的情况下擅自更改文件。审查就报告问题，修改需要先有对应指令。不应该因用户没有事无巨细地说清每一项规则就束手束脚，但更不应擅自越过用户划定的边界。
 - 任务空转(Task thrashing): 没有新问题或变化，读过、测过、审过的又来一遍。能回答当前问题的证据就复用；代码或验收条件变了，再补相关验证。做完、验证充分，就结束。
