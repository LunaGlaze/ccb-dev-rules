# DocDeAI

开发文档、代码注释、PR 描述、提交说明、任务报告和聊天回复等文字，其都是面向读者的，需要明确自然语言的用途是沟通和传递信息而非用最短路径完成任务。写作目标是让读者准确理解事实、条件和下一步操作，不追求篇幅、修辞或看起来完整的格式。

## 语言要求

项目落档内容（源码注释、数据文档、提交说明、PR 描述、仓库内说明文档）以英文为准；与人类沟通或专门要求的材料以用户使用语言为准。不要把沟通语言误用为改变游戏文本或源代码标识符的依据。中英文均应避免下文列出的 AI 味模式。

## 一、写作前核查

1. 明确读者是谁，这段文字要帮助读者完成什么。
2. 每个断言依据什么。具体数字、日期、来源、性能结果、兼容范围和完成状态必须能在仓库或用户提供的信息中核实。
3. 区分已经实现的行为、已决定的规则、计划中的工作和仍未确认的问题，不要把其中一种状态写成另一种。
4. 缺少依据时，提出问题或注明待确认，不用听起来可信的补充填空；确实影响任务完成时向用户提问，否则把补充建议放在正文之外。

### 1.1 读者身份

通常来说，文档的读者都是“第三方开发者/贡献者”，PR的阅读者还包括普通玩家，这些读者都不是任何智能体或与你对话的用户，故需要保证任何文档都是人类可读的，而非充满“AI味”的。应该让文档能让有基本编程基础但初次接触项目的人类能够理解涉及的各项功能，而非作为智能体自己的留言笔记或向用户汇报工作成果。

## 二、常见 AI 味（通用）

### A. 铺垫代替陈述

 - A.1 假对比（“不是 X，而是 Y”/“Not X but Y”）
   + 否定半边命名了没人主张的替代方案，用来抬高正面说法；对于两个没有因果或联系的事物进行先否定A再肯定B
   + 增加语气而不增加事实。直接陈述主题本身即可。
 - A.2 单句收尾与戏剧性碎片
   + 单独成段、重复前文结论，或将一句话拆成多个短句只为了制造停顿。
   + 要求读者停顿，却不提供新信息。
 - A.3 格言与伪深度
   + 用比喻或格言包装普通判断，却不给出具体细节。
 - A.4 起跑式铺垫
   + “接下来让我们深入看看”“以下是你需要知道的”“Let's dive in”“Here's what you need to know”等只预告下文的句子。
 - A.5 与假想敌辩论
   + “不要误会”“我不否认”“有人可能会认为……”“This isn't mainly about”“I'm not saying”等在没有实际异议时自我辩护。

### B. 节奏与结构公式化

 - B.1 强凑三段式
   + 为了凑三个词或三项而强行列举，例如“创新、突破和全新的可能”。
 - B.2 四字词排比
   + 空泛同义词堆叠，如“稳定可靠、快速响应、易于维护”。
 - B.3 句式开头复读
   + 连续多个句子用相同主语或相同介词短语打头，句式僵硬。

### C. 连接与标点公式化

 - C.1 破折号当万能连接
   + 反复用破折号制造悬念、掩盖分句关系，或一段中多处出现“——不仅如此——”。
   + 英文长难句不使用正确从句结构而使用`--`简化连接。
 - C.2 高频 AI 废话连接词
   + “值得注意的是”“不可否认的是”“毋庸置疑的是”“显而易见”“正如前文所述”“在此背景下”“归根结底”“从某种意义上说”。
   + 重复限定同一层不确定性，例如“could potentially possibly”。
 - C.3 “随着……的发展”式开头
   + 段落开头用“随着……的不断推进”“在……时代背景下”等引入，但背景本身没有独立信息。

### D. 拔高与借权威

 - D.1 AI 高频词与职场黑话
   + “赋能”“打通……闭环”“底层逻辑”“护城河”“矩阵”“全方位发力”“顶层设计”“至关重要”“深入探讨”“无缝”“标志着”“里程碑”等。
   + Actually, additionally, delve, crucial, pivotal, landscape, tapestry, testament, underscore, showcase 等高频 AI 词汇成堆出现。
 - D.2 意义拔高
   + “标志着新时代”“具有里程碑意义”“留下了不可磨灭印记”等无独立内容的套话。
 - D.3 虚假权威与模糊信源
   + “业内专家普遍认为”“相关行业报告指出”“不难看出”“众所周知的是”。
   + 说两件事有关联，却不说明如何关联，例如“associated with”“linked to”。
 - D.4 句尾补充式拔高
   + “彰显了团队对创新的不懈追求”“体现了……的卓越精神”等只重复赞美的尾巴。
 - D.5 宣传语与空洞赞美
   + “堪称……天堂”“卓越的”“革命性的”“惊艳的”“breathtaking”“stunning”“renowned”“groundbreaking”等没有参数或证据的褒义词。
 - D.6 借权威
   + 用未具名权威或媒体列表背书，例如“experts argue”“cited in The New York Times, BBC, Financial Times”。
   + 把“一些专家认为”改写成编造的机构、报告或日期，或将笼统归因写成确定事实。
 - D.7 回避“是／有 / is/are / has”
   + 用“充当”“具备”“展现”“serves as”“stands as”“boasts”等复杂书面词替代简单动词。

### E. 排版与格式

 - E.1 粗体当装饰
   + 在一句话里加粗 3–4 个专有名词或黑话，或每个列表项都用“加粗标签：”开头。
 - E.2 机械化加粗小标题 + 冒号清单体
   + 把所有内容拆成“加粗小标题：正文”的列表，即使不适合列表。
 - E.3 滥用装饰性 Emoji
   + 在小标题和正文中无意义堆砌 🚀 💡 🔥 📌 ✨ 🎯 等。
 - E.4 大面积加粗与破折号内心戏
   + 段落中多处大面积加粗，或频繁用“（当然，这并不绝对）”“（笑）”等插入内心戏。
 - E.5 装饰性标题
   + 标题首字母大写、加 emoji 或箭头、段落间加横线、标题与正文第一句重复。
 - E.6 引号与标点混用
   + 中文正文中混用英文半角标点或反之，或中英文之间缺少空格。

### F. 文风文体

 - F.1 滥用比喻与间接表意
   + 大量利用`像,好似,犹如,如同`等明喻词，链接两个毫无关系的事物或为没有任何可联系逻辑的事件
   + 不直白表达意思，非要用拐歪抹角的比喻、调侃、暗语来装腔作势，生硬违和
 - F.2 活化死物
   + 无理由地为死物赋予仅供活物使用的动作/动词，例如"The whole conversation is eating its own tail""Sometimes chaos expects you to remember it independently"
 - F.3 滥用否定
   + 高频用“没+动作”的否定表述替代正面刻画
   + 强迫性定义某种事物不是某种无关事物的废话表达，否定内容毫无必要，且与语境脱节

### G. 聊天与草稿残留
 - G.1 客服腔
   + “好的，没问题！”“这是一个非常深刻且具有前瞻性的问题”“希望以上内容对您有所帮助！”等。
 - G.2 知识边界免责与猜测填充
   + “截至我的知识库更新时间”“由于公开信息有限，推测可能……”等。
 - G.3 报幕式过渡句
   + “下面让我们一探究竟”“话不多说，直接上干货”“接下来看重点”。
 - G.4 首句复读标题
   + 标题之后紧跟一句重复标题的段落，再才是真实内容。
 - G.5 谈论上一稿/元叙述
   + “这一段是刚补充的说明”“前面改成了什么”等编辑过程残留。
   + 描述文档自身而非主题，例如“This function was added to replace the previous approach”。
   + “本文将探讨”“本节介绍导出限制。下面说明导出限制”等对文档自身的描述。

## 三、中文常见 AI 味补充

### 连接与标点公式化

 - C.zh.1 层叠的“的”字
   + 长定语层层嵌套，读起来像翻译腔。

### H.句式与词汇（欧化中文与机翻腔）

 - H.1 恶性被动句
   + “被广泛认为”“被成功实现”等生硬被动，施事者缺失。
 - H.2 过度名词化与动词虚化
   + “进行优化”“实现提升”“具有极高可行性”等。
 - H.3 同义词机械轮换与代词指代僵硬
   + 在“该产品”“此工具”“该平台”之间生硬倒换，或连续多句以相同代词开头。
   + 建议统一明确称谓，或用自然主语省略和动作衔接，不按字数强行替换同义词。

## 四、英文常见 AI 味补充

 - C.en.1 Hyphenated pairs
   + 名词后仍保留形容词短语的连字符，例如“the report is high-quality”。
 - D.en.1 Shallow -ing riders
   + 把 -ing 短语拼在简单事实后，制造深度感，例如“symbolizing”“reflecting”。

## 五、其他常见 AI 味补充

### I.机械性开发调研

 - I.1 超量引用代码
   + 在叙述中直接大量使用`...`引用原始代码片段，拒绝自己的总结
   + 单个短句中出现多个使用`...`引用原始代码片段加极少数未被代码块格式包裹的文本，引用量过半
   + 全篇文档有效信息只有被拆散的代码片段，缺乏自然语言说明

## 六、可以保留的正常人类表达

下列特征属于正常写作，不应仅凭单一特征就断定为问题并粗暴删除：

1. 地道的成语和文雅表达，如“事半功倍”“未雨绸缪”；英文中的惯用搭配和固定术语。
2. 孤立出现的过渡词，如偶尔的“然而”“与此同时”“however”“meanwhile”；只有在每段开头机械重复时才治理。
3. 技术或学术场景的必要被动与规范句式，如“实验数据由传感器自动记录”“The data is recorded by the sensor automatically”。
4. 适合列表的内容，如 API 参数、会议代办，无需强行改成叙述文。
5. 作者有意的修辞排比，如“他来了，他看见了，他做到了”“She came. She saw. She conquered.”。
6. 具体、不寻常的细节和真实的个人体验，如真实地址、具体引文。
7. 混合感受和未解决的张力，如“我想这大部分不错，但有点让我在意，又说不清为什么”“I think this is mostly good, but it bothers me, and I can't fully explain why.”。
8. 时代限定的引用、行话和内部笑话。

## 七、写作与交付前核对

1. 通读全文，判断文体和读者，记住需要保留的主张、数据、关系和限定。
2. 按第二~六节逐条核对，只修改确实存在的表达问题；重复的同一信息可以合并，不同信息不能因排比或篇幅而删掉。
3. 对照原文检查改写：有没有新增、遗漏或强化主张；施事者、时间、条件、范围、否定与归因是否一致。
4. 检查“可能”“据称”“超过”“仅”“正在”“计划”以及英文中的“may”“likely”“allegedly”等词承载的含义，不要求逐字保留，但不得改变确定程度。
5. 通读成稿，检查语气和衔接；不要为了展示工作量强行修改已通顺的文字。
6. 每个新增的具体信息必须能在原文或用户材料中找到，找不到就撤回。
7. 文件的代码块、行内代码、命令、路径、URL、链接目标、YAML 前言和数据保持原样；不因润色改变含义或可复制性。
